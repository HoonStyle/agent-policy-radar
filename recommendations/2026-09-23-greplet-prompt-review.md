## 최초 로컬 검토 범위 (배포 판단 근거로 단독 사용하지 않음)

`greplet` HEAD `3fda3e7`의 현재 작업 폴더 기준. README/indexer 소스 등에 미커밋 변경과 여러 미추적 문서가 있어 HEAD만으로 현재 상태 전체를 식별할 수 없다. 본 검토는 아래 예제 skill 및 MCP 도구 설명과 관련 CLI 구현을 읽은 정적 검토다. 서비스 기동·재인덱싱·DB 읽기/쓰기·모델 호출·검색 성능 시험은 하지 않았다. 대상 root/깊이 2 이내 AGENTS.md/CLAUDE.md는 발견되지 않았다.

대상:
- `examples/claude-code-skill/SKILL.md`
- `examples/codex/skills/greplet/SKILL.md`
- `mcp-server/src/index.ts`, `mcp-server/src/greplet.ts`
- `greplet-mcpb/server/index.js`의 evidence 도구 설명
- `greplet.mjs` 옵션 처리, `indexer/start-indexer.sh` 기동 동작

배포 예제를 검토했으며 모든 실제 설치본의 로딩·동작을 확인한 것은 아니다.

## 1. 우선 수정: 검색 청크와 최신 원문 근거 구분

근거: Claude skill:72, Codex skill:57은 ‘청크만으로 답이 되면 그대로 정리’하도록 한다. 예제에는 `evidence-search`/`evidence-get` 또는 MCP evidence 경로 사용 안내가 없다. 반면 `mcp-server/src/index.ts:115-169`와 MCPB는 evidenceRef 조회 및 원본 파일 hash 재검증/404·409 반환 도구를 이미 제공한다.

문제: 인덱스 청크를 현재 파일의 검증된 근거로 오해할 수 있다. 후보/스니펫의 관련성과 원문 최신성은 별개다.

최소 제안: 일반 탐색은 기존 청크로 위치를 좁히되 최신 코드 판단·인용·수정 근거로 사용할 때 현재 원문 또는 제공된 evidence 조회로 확인한다. 404/409는 확인 실패·오래된 근거로 표시하고 변경 승인으로 해석하지 않는다. 해시 일치 역시 자연어 주장의 의미 정확성을 보증하지 않는다. 모든 짧은 검색에 evidence 호출을 의무화할 필요는 없다.

## 2. 우선 수정: ‘그 파일만/그때만’ 폴백 제약

근거: Claude skill:73,78 / Codex skill:58,63. 서버 없음 또는 결과가 비었을 때만 폴백하고, 검색된 파일만 읽도록 제한.

문제: 결과가 비어 있지 않아도 무관하거나 누락·오래됨·잘못된 workspace일 수 있다. 반환된 파일만 검토하면 후보가 발견하지 못한 정의·호출자·설정의 확인을 막는다. 동시에 정확 문자열 전체 출현과 완전성은 rg로 확인하라는 다른 항목도 존재한다.

최소 제안: greplet을 유용한 탐색 선택지로 두고, 결과가 불충분/무관/오래됐거나 의미 판단에 다른 파일이 필요하면 허용된 범위의 Read/rg/LSP로 보완한다. 무조건 전체 스캔은 피하되 필요한 범위 확장을 일괄 금지하지 않는다. 새 모델이 더 강하게 지침을 따를수록 이 제한을 실제 검색 금지로 읽을 수 있으나, 새 모델에서 그 실패를 실측한 것은 아니다.

## 3. 확인된 예제-구현 불일치: --all과 --workspace 동시 사용

근거: Codex skill:41의 ‘자주 쓰는 조합’은 `--all --full --workspace docs`를 함께 사용한다. `greplet.mjs:350`은 `args.all ? "all" : [workspace]`로 전달하므로 docs로 제한되지 않는다.

최소 제안: 해당 예제에서 `--all`을 제거하거나 전체 검색 예제와 분리. 대상이 분명하면 workspace를 지정하라는 기존 설명과 맞춘다. MCP evidence 검색도 `workspaces` 기본이 all이므로(`mcp-server/src/index.ts:126`, MCPB:248), 도구 설명에서 대상이 정해졌을 때 명시적 workspace 목록 사용을 안내할 수 있다. API 기본값 변경은 별도 호환성 결정이며 이번 문구 검토만으로 변경하지 않는다.

## 4. 운영 경계 후보: 조회 실패를 서비스 기동 지시로 연결

근거: 두 skill의 ‘안 떠 있으면 기동’, `mcp-server/src/greplet.ts`의 backendDownMessage는 미가동뿐 아니라 일반 요청 실패에도 기동을 안내한다. `start-indexer.sh`는 백그라운드 프로세스를 시작하는 실제 운영 작업이다.

최소 제안: 단순 조회 실패가 무조건 서버 부재라는 뜻은 아님을 구분한다. 기존 허용 범위/운영 지침 내에서만 기동하고, 환경이 없으면 관련 로컬 검색을 계속한다. 재인덱스나 설정 변경까지 조회 요청의 허가로 확대하지 않는다. 매번 새 승인을 강제하자는 뜻이 아니라 자동 기동 가정의 범위를 명확히 하자는 제안이다.

## 5. 성능·구성 단정 완화

근거: 두 skill description과 목적 문단은 ‘~2초’, ‘통째로 grep/read 하면 느리고 토큰을 많이 쓴다’를 조건 없이 제시하며 bge-m3/Roslyn/PdfPig 구성을 고정 설명한다.

최소 제안: ‘관련 후보를 좁혀 반환한다’로 설명하고, 시간·토큰 이득은 인덱스 크기/워밍/임베딩/조회 조건에 따른 측정값으로 분리한다. 특정 설치 구성은 예시 또는 현재 설정으로 표시한다. 이번에는 실제 지연이나 절감률을 측정하지 않았으므로 비용 절감 효과를 주장하지 않는다.

## 유지할 부분

- 파일명/방금 수정한 파일 확인은 기본 파일 도구 사용.
- 호출 관계·상속·참조 질의는 LSP 등 구조 도구 사용.
- 검색과 생성의 구분, 정확 문자열/완전성의 추가 확인.
- 작은 topN과 대상 workspace 우선, 원문 위치 표시.
- 원격 MCP의 인증 및 읽기 전용 범위. 검색 결과가 정확하다는 보증으로 해석하지 않음.

## 적용 제안

우선 1·2·3의 근거/조회 범위/예제 정합성을 고친 뒤 4·5를 간단히 다듬는 순서가 적절하다. 양 하네스 예제와 원격 MCP/MCPB 설명의 취지를 맞추되 기능 확장이나 새 하네스 규칙을 중복 추가하지 않는다. 실제 적용은 사용자가 승인한 뒤 greplet 프로젝트에서 진행한다. 이번 검토에서는 진행 중인 파일을 포함해 greplet의 어떤 파일도 변경하지 않았다.
