# Presentation Design

Add art direction and review to the host's presentation toolchain. This skill is not a PPTX renderer or an Office automation engine.

## 1. Establish the deck contract

Read the existing deck, reference/template, audience, purpose, content sources, and delivery context. Distinguish live presentation from a reading deck. Preserve requested slide count, aspect ratio, language, facts, masters/layouts, brand assets, editability, and speaker notes. Reuse established information before asking questions. A review-only request produces findings, not changes.

Read the [shared design foundation](../design-director/references/shared-foundations.md) when establishing or coordinating the visual system. Read [slide craft and QA](references/slide-craft.md) before new layout work. Complete this step with a short outline and a clear boundary for what may change.

## 2. Build a content-led storyboard

Give each slide a specific purpose and a descriptive, distinctive title. Write the main message and its evidence before choosing the layout. Use [storyboard.md](assets/storyboard.md) only when it helps organize substantial work.

Choose evidence-led compositions: comparison, process, timeline, data, image-led explanation, or focused narrative as appropriate. Avoid the same panel grid, decorative metric tiles, or slogan on every slide. Vary density where the story benefits while preserving a consistent visual system. Do not manufacture claims or charts to fill space.

For a supplied template, map content into its existing layouts and preserve intentional repetition. For a new deck, establish representative dense and sparse slides with real content, then extend the system. Respect the agreed scope instead of demanding new concepts for a local edit.

## 3. Author with the existing presentation workflow

Discover and read the host's presentation skill/tool before authoring. If Codex Presentations is installed, use its specified runtime, Artifact Tool, template handling, export, and finalizer; this package does not replace those requirements. Resolve tools at runtime instead of assuming a global binary, absolute package path, or external account exists.

When no host toolchain is prescribed, use the project's already-approved native/template workflow. Other tools such as PptxGenJS or Pandoc are candidates only after capability and environment checks, not automatic fallbacks. Do not install a renderer or start a cloud conversion merely to satisfy this skill.

Map approved brand colors and type to masters/theme definitions where supported. Keep fonts, chart labels, units, and native tables/charts editable when required. Preserve embedded data and formulas rather than replacing them with a visual approximation. Use actual available fonts with Korean/English glyph coverage. Do not shrink content indiscriminately to force a slide count.

If authoring or rendering is unavailable, finish the storyboard/design assessment and state the missing capability. Do not claim a PPTX was produced or visually verified. Publishing, sharing, and live configuration changes remain outside ordinary local authoring scope.

## 4. Render and review the deck

Run the host's structural/export checks, render every final slide, inspect individual slides at readable size, and review deck-level rhythm. Use the craft reference to check text fit, evidence, hierarchy, color, image crop, reading order, accessibility, and editability. Review relevant language versions separately.

Fix only concrete scoped findings, export a new revision, and repeat affected checks plus a whole-deck consistency scan. Keep source and prior revisions intact. State which renderer or Office application actually ran; a successful package parse is not proof of native PowerPoint fidelity.

Deliver the requested editable deck and concise limits, not an unsolicited bundle of QA images. When the task is only a design review, provide findings with slide number, observation, impact, and proposed fix.
